# API and realtime contract

## Protocol 5 — 5 November 2026, B048

Public `GET /api/v1/rooms/:code` exposes invitation availability/settings with a 30/minute IP limit, without roster or answers. Authenticated `GET /api/v1/recovery` returns valid rooms and removal/expiry notices; `/resume` remains. New intents: `settings.update` (owner, lobby), `appearance.update` (self, lobby/results), `adult.confirm`. Snapshots include pace/guided voice, adult confirmation, invitation URL and narration state. Eligible choice phases support STT under the same recording cap. Generated [HTTP](api/openapi.json) and [socket](api/sockets.json) schemas are authoritative. [Full behavior](ROOMS_AND_GUIDED_VOICE.md).

## Fields introduced with protocol 4 — 4 November 2026, B045

B045 required protocol 4; B048 now requires protocol 5. Old clients receive `CLIENT_UPDATE_REQUIRED`. The fields below remain in protocol 5. Saved game rules and host flow are versioned independently. Generated [socket schemas](api/sockets.json) and [OpenAPI](api/openapi.json) are authoritative.

- Room setup adds `hostLanguage: en | hi | hinglish`. Audio start adds per-recording `language: en-IN | hi-IN | te-IN`, with optional `hostBeatId`/`hostTurn` for invitations.
- Private audio messages include completed `segment` text and final `transcript`. They go only to the authenticated speaker. Recording attempts are server-persisted, two per answer/host turn.
- Submissions may include `original` and `language`; `text` is the player-confirmed gameplay answer used for scoring. Only released originals/translations appear in `revealedSources`.
- Snapshots add `hostFlowVersion`, `hostBeat`, remaining recordings and confirmed public reply text. The host beat exposes status, captions/audio URL, invitee, turn and deadlines; private preparation/provider context stays server-side.
- `host.reply` carries CID, beat ID, turn, text, optional original/language and outcome `answer | pass | stt-failed`. The server checks seat ownership, invitation, deadlines, CID/body hash and confirmed nonempty answers. Timeout is generated by the server.
- `POST /api/v1/rooms/:roomId/translate` accepts run/connection IDs, phase epoch, original text, speech language and optional host beat/turn. It returns `{text, language}` privately. Identical preparation requests are cached/deduplicated; late or out-of-turn requests are rejected. Failure leaves manual correction available.

The earlier protocol-3 and Tap-to-ask descriptions below are historical/legacy behavior. See [current director and compatibility](INTERACTIVE_HOST.md).

**Coverage limit:** OpenAPI currently documents route inventory, request bodies, path parameters and generic errors. Success bodies below are read from code; they do not yet have generated schemas or Fastify response validation. ## Authentication and REST payloads

Except health, guest creation/update and callback-token authentication, the routes require the guest cookie. All application write methods and both socket upgrades require an exact allowed `Origin`; webhook writes use the job token instead. Cookies are HttpOnly/SameSite=Strict and Secure for HTTPS. No CORS-based cross-origin client deployment is configured; use the single origin proxy. Guest identity is separate from room-seat identity; see [database identities](DATABASE.md#identities-and-relationships).

There is no HTTP endpoint for starting/voting/kicking/approving a card: those are realtime intents. There is no public profile-history, admin-cost-dashboard, guest-erasure, room-settings-update, or realtime webhook subscription endpoint. Operator tools are local CLI commands.

The DeepSeek or Gemini host request is outbound HTTPS from the backend after an accepted `host.ask`; it is not a browser API or a player WebSocket to the model provider. Only the current speaker's question, public phase, names, scores and fixed rules are sent. Submitted private answers are not included. The completed reply is published through the authorized room socket, then Gnani TTS may generate its audio.

## Client sequence

1. Establish guest cookie, create or join a room, then open realtime with an allowed Origin.
2. Send `connect` with protocol 3, room ID, last revision and `takeover:false`. Receive ownership UUID and a full permitted snapshot. A second active tab gets `SEAT_IN_USE`; only an explicit `takeover:true` revokes the first writer.
3. Submit an intent containing unique `cid`, run ID, step ID and phase epoch. Keep pending until both an accepted acknowledgment and its state revision arrive, in either order. Display typed rejection and refresh if the phase ended.
4. On reconnect, resend only unacknowledged intents with their original IDs/payloads. The server returns existing receipts and a fresh snapshot. Older revisions are ignored. There is no local online-mode progression.
5. Before voice, send a start frame with the current server connection ID and phase identifiers. Wait for ready, send 1,024-byte binary frames at 32 ms cadence, then Stop. Completed transcript segments are editable text; text submission is a separate action.

The real message envelope is `{protocol_version:3,type:"intent",runId,intent:{cid,stepId,phaseEpoch,...action}}`. `cid` is a client action ID (the frontend generates UUIDs). Acks contain `{type:"ack",cid,revision,accepted,code?,message?}`; many invalid game actions use `ACTION_REJECTED` plus a specific message. Transport/auth/ownership failures use socket `error` messages. All intents are matched against the controlling seat; the client does not get to supply the actor identity.

Supported intent families include ready/start/kick/chat; traits/nominate/submit/vote/predict; skip/veto/next; approve/reject/restart. The current phase, role and pending status decide which actions are valid. `lastRevision` is accepted in connect but not used for incremental replay; the server sends full permitted state. Unacknowledged intents can be resent by the live adapter after reconnect; a page reload loses that in-memory pending queue but recovers already committed state.

Each connection has a 30-second lease renewed by `ping`; actual socket close immediately marks disconnection. Grace/takeover rules then apply. A second connection requires `takeover:true`; the old socket gets `SEAT_TAKEN_OVER` and closes. Network protocol 3, online flow version 3 and offline checkpoint version 2 are distinct version fields.

Audio start also carries `captureId`, `purpose:"answer"|"host"`, `diagnosticConsent`, `sampleRate:16000`, room/run/step/epoch and the realtime `connectionId`. Stop/cancel are JSON control messages, PCM is binary. Returned segments are completed STT segments, not speculative word-by-word partials. The final message carries editable text and an optional diagnostic media ID; it never submits a game answer itself.

## Lobby chat

Lobby chat uses a `chat` intent with 1–240 trimmed characters. Seat ownership, membership, phase and deduplication use the same transactional checks as game actions. The server assigns the sender identity and timestamp. Five messages per seat per ten seconds and a 50-message history bound room traffic. Messages persist in the private match snapshot, survive new arrivals/reconnects, are projected in the pre-game lobby and post-game summary, and follow seven-day snapshot content retention. A rematch copies the latest 50 messages to its new snapshot. Chat is closed during active questions and reopens at summary; it never changes scores or enters host prompts. Only the host can start, after all configured seats have joined and every participant is ready.

The host has separate Ready and Play controls. Readiness includes the host; undoing it disables Play again. Accepted Start moves every client into the existing trait/self-and-friend-rating phase. Merely backgrounding a tab silences its media but does not voluntarily disconnect its healthy online socket; socket loss, page exit and expired heartbeats still trigger the agreed presence rules.

`kick` is a normal deduplicated intent with a target `playerId` (seat UUID). Only the controlling room host can use it, only in the lobby, and never on themselves. The transaction marks `room_members.removed_at`, revokes ownership, rebuilds the pre-game roster and frees the seat for a replacement. Capacity stays as configured; the host waits for the replacement to join and ready. Removed guests lose snapshots, resume, media/card access and rejoining with that guest identity. They receive a terminal membership message and a home action; the client stops retrying. A fresh guest identity is not a durable abuse ban in this private release.

`host.cancel` carries a `conversationId` UUID. Only the active speaker's controlling connection can cancel; a stale ID cannot cancel a later exchange. Dismissal releases the pause immediately, restores remaining phase time and aborts an active provider request. Unsent exchanges return their slot; submitted exchanges remain consumed for that intermission. Duplicate cancellation is harmless. Responses completing after cancellation cannot restore the pause. Browser dismissal supports outside click, Escape, Close and Back to the room, and cancels microphone capture. Speaker disconnection also releases the slot.

## Diagnostic callback reliability

Each batch job gets a random 32-byte callback token, stored hashed and redacted from request logs. Payload size, job association and event type are validated. Inbox rows deduplicate notifications; endpoint acknowledgment does not mean the result is verified.

The reconciliation worker queries authenticated Gnani status/results even if callbacks are absent. It polls every 30 seconds while running; pg-boss cron also restores scheduled reconciliation after restart. Duplicates, delayed notices and out-of-order terminal notices cannot overwrite local cancellation/expiry. Transcript downloads accept only HTTPS provider/S3 hosts and no redirects. The application does not invent a provider signature scheme.

The earlier provider research used [Gnani batch documentation](https://docs.gnani.ai/api/STTBatch/Introduction) for best-effort callbacks and authoritative polling; this audit verified the local implementation, not live account delivery. Jobs with an uncertain create response and no provider job ID remain uncertain for operator reconciliation rather than being blindly submitted again. Completed/failed/cancelled local jobs are not repolled solely because a later notification arrives. No webhook signature verification is implemented; an actual account signing contract remains to be confirmed.

## Operational limits

This is one private backend instance. HTTP/socket payload limits and rate limits bound accidental traffic, not a complete public-service abuse defense. The supplied suite tests ten concurrent rooms with test rate limits disabled to isolate engine/database correctness; public launch needs load/abuse tuning and trusted proxy handling. Provider quotas are enforced separately under PostgreSQL locks.

HTTP limits use verified guest identity for authenticated requests, avoiding a shared tunnel/NAT budget for an entire squad. Missing/invalid cookies share their IP budget; inventing cookie values does not create new budgets. Guest creation remains IP-limited. Exhaustion returns a typed `RATE_LIMIT` rejection. A separate integration check runs with limits enabled and verifies isolation and invalid-cookie fallback.

Current limits in `server.ts`: 120 HTTP requests/minute per verified guest or anonymous IP; guest creation/update 20/minute per IP; realtime 80 messages/10 seconds per connection and 64 KiB socket payload. Default HTTP/callback body limit is 256 KiB; clip upload allows 450,000 bytes, with additional decoded WAV validation. `trustProxy:false` means anonymous requests through the local tunnel/proxy share the loopback budget. This remains a private-playtest configuration.

## Optional media events — 2026-11-03

Protocol remains 3. Connect may include `capabilities: ["media-events-v1"]`. Only opted-in connections receive `{type:"media.changed",runId}` after committed clip consent/upload, deletion or expiry removal. The event contains no author, answer, clip URL or audio. Eligible visible owners re-fetch the existing authorized media list; legacy clients receive no new message and retain their polling behavior. Reconnect and reveal entry revalidate the list if an event was missed. Shared schemas and generated sockets.json include this capability.

Room broadcasts now coalesce concurrent invalidations, load committed state once inside a transaction, and project separately for each recipient. Membership and current connection ownership are checked per recipient; stale writers are closed. Revisions cannot go backward within a run. The 10-second lease heartbeat is unchanged. Client initialization/resume are single-flight; retry backoff includes jitter, pauses offline, and stops terminally on ownership rejection. No paid action is synthesized by reconnection.

## Room experience revision — 3 November 2026

Duplicate display names are normalized (Unicode NFKC, collapsed whitespace, case-insensitive comparison) and numbered in seat order within the room. Literal numbered names are reserved to prevent collisions. Saved guest profiles are unchanged; projected chat names resolve by seat ID. Any controlling participant may send chat at summary; only the host can submit restart. Restart resets scores/readiness but carries the bounded chat history. No protocol or schema change.
